## Warnings

### WR-01: EndMessage silently dropped when worker is restarting (mid-request data loss)

**File:** `packages/proxy/src/response-handler.ts:128`

**Issue:** `fireAndForgetEnd` sends the EndMessage to the worker only when `w.isReady()`.
If a non-collector request started while the worker was ready, but the worker crashes and
re-enters "starting" before `onClose`/`onError` fires, the EndMessage is silently dropped
— no log, no fallback, no entry written to the DB. This is a narrower form of the same
data-loss the PR is fixing.

The `collectorRequestIds` Set only protects requests where the worker was already stopped
*at Start time*. There is no path that handles the case where the worker was ready at
Start time but stopped/restarting by End time (for non-chunk, non-collector requests).

```typescript
// current code (line 127-130)
const w = getUsageWorker();
if (w.isReady()) {
    w.postMessage(msg);
}
// silent drop if state === "starting" — no log, no fallback
```

**Fix:** Add an `else` branch to log the data loss, matching the existing warn in
`safeHandleChunk`:

```typescript
const w = getUsageWorker();
if (w.isReady()) {
    w.postMessage(msg);
} else if (!collectorRequestIds.has(msg.requestId)) {
    // Worker became unavailable mid-request; the Start was already sent to the worker.
    // We cannot retroactively re-route, but at least log so the loss is observable.
    log.warn(
        `fireAndForgetEnd: EndMessage dropped for requestId=${msg.requestId} — worker state is "${w.getHealth().state}"`,
    );
}
```

### WR-02: Grace-period timer in terminate() is not stored — cannot be cancelled

**File:** `packages/proxy/src/usage-worker-controller.ts:244`

**Issue:** The fallback `setTimeout` inside `terminate()` is not assigned to a class
field. If `terminate()` is called concurrently or the `Promise` resolves via
`shutdownResolve()` before the 2 s grace elapses, the orphaned timer fires a second
`resolve()` call on an already-settled Promise — harmless due to Promise semantics, but
it also means the timer cannot be cancelled if `terminate()` is called a second time or
tested in isolation. The stale timer will keep the test process alive for an extra 2 s.

```typescript
// current (lines 240-247)
const promise = new Promise<void>((resolve) => {
    this.shutdownResolve = resolve;
    setTimeout(() => {        // ← not stored, cannot be cleared
        resolve();
    }, SHUTDOWN_GRACE_MS);
});
```

**Fix:** Store the timer and clear it in the `.then()` callback:

```typescript
let graceTimer: ReturnType<typeof setTimeout>;
const promise = new Promise<void>((resolve) => {
    this.shutdownResolve = resolve;
    graceTimer = setTimeout(() => {
        resolve();
    }, SHUTDOWN_GRACE_MS);
});

return promise.then(() => {
    clearTimeout(graceTimer);
    this.destroyWorker();
    this.state = "stopped";
});
```

### WR-03: Test 4 does not prove timer cancellation — assertion window is too short

**File:** `packages/proxy/src/__tests__/usage-worker-controller-restart.test.ts:193`

**Issue:** Test 4 ("terminate() during backoff cancels the pending restart timer")
verifies `getWorkerCreateCount()` did not increase after a `sleep(50)`. The real backoff
delay is `computeBackoffDelay(0) = 1000ms`. The 50 ms sleep window means the assertion
would pass even if `clearTimeout(this.restartTimer)` were removed entirely — the timer
simply hasn't fired yet within the observation window. This makes the test a false
positive for timer cancellation.

**Fix:** Either:

(a) Use a fake timer / mock `setTimeout` to advance time deterministically and assert the
callback never fires after `terminate()`:

```typescript
// Preferred: mock setTimeout so the backoff fires immediately in test time
// then verify workerCreateCount did not increase
```

(b) Expose an observable hook (e.g., `getRestartTimerPending(): boolean`) and assert it
returns `false` after `terminate()`:

```typescript
await controller.terminate();
expect(controller.getRestartTimerPending()).toBe(false);
```

Until a fake-timer approach is in place, add a code comment acknowledging the limitation
so future contributors don't mistake the test for proof of cancellation.

### IN-01: Test 8 comment claims Set-emptiness verification, but only checks call counts

**File:** `packages/proxy/src/__tests__/response-handler-worker-protocol.test.ts:728-733`

**Issue:** The test comment says "The Set must be clean" and "verify no leak", but the
actual assertion is `expect(mockCollector.handleStart.mock.calls.length).toBe(2)` — it
counts call invocations, not Set contents. If a requestId were *not* deleted from
`collectorRequestIds` after End, the Set would leak but the call-count assertion would
still pass. The test would miss a future regression that forgets to call
`collectorRequestIds.delete()`.

**Fix:** Either update the comment to accurately describe what is being tested ("Two
requests each called handleStart once"), or add a test that calls `resetForTesting()`,
starts a new request with the same requestId, and asserts it is treated as a fresh
request (which would fail if the Set leaked the ID).

### IN-02: Type cast workaround in aliasing test documents a now-resolved type mismatch

**File:** `packages/proxy/src/__tests__/worker-transfer-aliasing.test.ts:140`

**Issue:** The test assigns an `ArrayBuffer` to `ChunkMessage.data` with
`as unknown as Uint8Array`. The actual `worker-messages.ts` definition correctly types
`ChunkMessage.data` as `ArrayBuffer` (confirmed at line 73). The cast is unnecessary and
misleading — the comment on line 138 says "cast to test runtime shape" but the type is
already correct, making the cast a no-op that obscures intent.

**Fix:** Remove the cast:

```typescript
const msg: import("../worker-messages").ChunkMessage = {
    type: "chunk",
    requestId: "req-alias",
    data: buf,   // buf is already ArrayBuffer — no cast needed
};
```
